# VDI NAS 性能压测与容量验证（实测案例参考）

> 来源：WorkBuddy 资料库《VDI NAS 性能测试》归档（成果汇总 / 全过程记录 / 踩坑手册 三篇），
> 归档于 2026-10-11。本文为**脱敏、技能导向**的整合版：删去真实 IP、主机名、账号，仅保留
> 可复用的测试方法、调优项、根因诊断套路与踩坑清单。**所有 `<...>` 均为占位符**，落地到自己设备时替换。

## 一、一句话结论

- 顺序大块吞吐、SSD 卷随机读写能力**均充足**；靠 NAS 侧一条静态路由，把跨网段读吞吐从 ~113 提升到 ~1125 MiB/s（约 10 倍）。
- 但「350 并发 · 32 KiB · 78% 写」的**验收口径仍未达标**（写 >50 ms 占比 19.30%，判 FAIL）。瓶颈在存储写路径稳态，与路由/网络修复无关。
- 针对「仅承载 D 盘 OST 文件」这一具体需求，实测能力有 **11–25 倍余量**，判断可承受（须满足 3 个硬前提）。

| 物理磁盘 | 12 块，全部 normal |

## 三、测试通路定义（三盘指向同一/不同物理卷）

三盘为 NAS 存储的不同访问路径，D 与 Y 指向同一物理卷（volume2 SSD RAID5），仅协议栈不同。

| 盘符 | 通路类型 | 后端存储 | 说明 |
|---|---|---|---|
| D: | 数据盘 vmdk（ESXi 数据存储） | volume2 · SSD RAID5 | 与 Y 同卷，走 ESXi 通路 |
| Y: | SMB 映射 `\\<NAS_IP>\nas-ssd` | volume2 · SSD RAID5 | 主压测目标 |
| Z: | SMB 映射 `\\<NAS_IP>\home` | volume1 · HDD RAID6 | HDD 基线 |

> 三盘关系：D 依赖 ESXi 数据存储通路（非 Guest 侧挂载）；Y、Z 为用户手动映射的 SMB 网络盘。

## 四、成果矩阵（当前最优配置）

最优配置 = NAS 双万兆静态路由修复已生效 + SMB 低风险调优（Multichannel + AIO 读）已开启。单位 MiB/s。

| 用例 | D（ESXi 通路） | Y（SMB · SSD） | Z（SMB · HDD） |
|---|---|---|---|
| 顺序写 1 MiB · qd16 | 1076.1 | 1105.7 | 849.3 |
| 顺序读 1 MiB · qd16 | 1121.1 | 1125.2 | 1082.3 |
| 顺序读 1 MiB · qd1 | 807.7 | 841.7 | 812.6 |
| 随机 32 KiB · 78% 写 · qd16（写/读） | 796.2 / 225.0 | 704.7 / 199.1 | 88.3 / 25.2 |
| 随机读 P95（ms） | 3.42 | 2.57 | 61.60 |

## 五、两项修复的收益（前后对照）

| 项目 | 修复前 | 修复后 | 提升 |
|---|---|---|---|
| 读吞吐（顺序读 qd16） | 112.8 MiB/s | 1125.1 MiB/s | 9.98× |
| 读延迟 P95（qd16） | 141.56 ms | 15.93 ms | −89% |
| 写吞吐（64 并发） | 278.0 MiB/s | 316.1 MiB/s | +13.7% |
| 读 P95（64 并发） | 21.889 ms | 11.993 ms | −45.2% |

两项修复：① 静态路由修复（跨三层下行读响应改走万兆口）；② SMB 低风险调优（仅开 multichannel + aio_read）。

## 六、验收判定（规格口径）

规格判据：块 32 KiB、随机、78% 写、每 VM outstanding=350、预热 5 min + 正式 30 min；稳态 P95 < 10 ms、早高峰 P95 < 20 ms；>50 ms 抖动样本占比 > 1% 即 FAIL。

| 指标 | 实测 | 判据 | 判定 |
|---|---|---|---|
| 写吞吐 | 214.7 MiB/s / 6871 IOPS | — | — |
| 写 P95 | 145.75 ms | < 10 ms | FAIL |
| 写 >50 ms 占比 | 19.30% | ≤ 1% | FAIL |
| 读 P95 | 139.46 ms | — | — |
| err | 0 | 需为 0 | PASS |

> 即便取历史最好一次（SMB 调优后缩短口径：写 298.4 MiB/s、写 P95 55.31 ms、>50 ms 占比 5.98%），三项判定同样全部 FAIL——350 并发档在任何口径、任何状态都未达标过。

## 七、关键洞察

1. **顺序 IO 无法区分介质与通路**：三盘顺序读写都在 849–1125 MiB/s，HDD 顺序读也能到 1082 MiB/s。
2. **随机 32 KiB 才是分水岭**：SSD（D/Y）随机能力是 HDD（Z）的 8–9 倍，随机读 P95 相差 20 倍（Z 为 61.6 ms）。VDI 启动风暴与系统盘 IO 全为随机小块，因此**用户盘必须放在 SSD 卷**。
3. **读瓶颈的根因是 NAS 路由，而非 SMB / RAID / 介质**：NAS 默认网关指向千兆口 eth0，跨三层下行（读响应）被限约 948 Mbps；上行（写数据）走万兆口 eth2 不受影响，因此出现「写 8.4 Gbps、读约 1 Gbps」的反直觉现象。
4. **验收 FAIL 的瓶颈在存储写路径稳态**，与路由/网络修复无关；且 30 min 长时口径明显差于 10 min 缩短口径，疑似 BTRFS(CoW) 数据集长期覆写后的碎片化。
5. 报告列出的峰值均为 best-case 能力上限，**不等于验收达标**。

## 八、全过程 10 阶段速览

| 阶段 | 目标 | 关键结论 |
|---|---|---|
| 0 环境接入 | DSM Web API 连 NAS、清点共享/存储 | volume1=HDD RAID6、volume2=SSD RAID5，均 btrfs |
| 1 挂载与数据集 | 先跑 Z(HDD) 后改 Y(SSD)；建 100 GiB 数据集 | SMB 登录需 `.\` 前缀；复用会话规避 1219 |
| 2 主压测 | HDD vs SSD 对照（32K/随机/78%写/350/qd16） | SSD 写 P95 47.97ms(FAIL)，HDD 2004.9ms(92%>50ms, FAIL) |
| 3 并发梯度 | 扫描 32/64/128/256/350 | **达标拐点=64 并发**；写带宽约 280–290 MiB/s 触顶 |

| 5 归因实验 | 1 MiB 顺序读写分离 | 读存在独立 ~113 MiB/s 硬上限，否定「RAID5 写惩罚主因」 |
| 6 通路对照 | SMB(Y) vs ESXi(D) 同卷 | 同卷换通路差 4–10 倍，瓶颈在 SMB/网络 |
| 7 根因锁定 | NAS 默认路由走千兆口 | 加静态路由使客户端网段走万兆口，读 112.8→1125 MiB/s |
| 8 三盘统一 | 修复后 D/Y/Z 重测 | 见第四节成果矩阵 |
| 9 验收重测 | 350 并发不同口径 | 规格口径 FAIL；短口径反而更差（疑似 CoW 碎片化） |
| 10 需求评估 | 仅承载 D 盘 OST | OST 100%随机/4–8K/67%读；350 台聚合中档 ~41 MiB/s、重档 ~82–328 MiB/s，实测有 11–25 倍余量 |

## 九、踩坑手册（精简，按类）

### SMB 挂载与文件操作
- **挂载报错 1219（多重连接）**：同账户已有映射会话，重复传用户名即冲突 → 不重复传用户名，复用既有会话映射新共享。
- **登录被拒/凭据错误**：NAS 未加域，默认按域账户认证 → 用户名加本地标识前缀，如 `.\<管理员账号>`。
- **删除网络盘文件被删除守卫拦截**：安全策略拦截网络路径上的常规删除 → 用 `System.IO.File.Delete` 直删。
- **数据集创建极慢（~27 MB/s）**：单进程 4 KiB 小串行写入 → 改多进程并行 + 1 MiB 块，提速至 ~83 MB/s。

### DSM Web API 与配置修改
- **SMB 配置写入返回 2001/101**：接口虽声明支持 JSON，实际要求**表单编码**，且必须用 **v3** 版本。
- **只传要改的字段仍返回 2001**：该接口为**整体覆盖**语义，不支持增量补丁 → 先读出完整字段集，整体回传并只覆盖目标项。
- **凭据连接报 unknown url type**：主机变量缺协议与端口 → 写成完整地址，如 `http://<NAS_IP>:5000`。
- **存储卷/池信息接口返回 101**：旧接口在当前 DSM 版本不可用 → 改用 `SYNO.Storage.CGI.Storage load_info`。
- **静态路由接口参数报 4302**：接口仅暴露 get/set，字段格式未公开 → 走 DSM 控制台 UI，或改用**开机任务计划**脚本固化。

### 压测工具（fio / DiskSpd）
- **判定始终 PASS、>50 ms 占比算成 0**：fio 用 `json` 输出不含延迟直方图 bins → 改用 `json+` 输出，解析时校验 bins 是否存在。
- **fio 目标路径落到错误位置**：该版本对含冒号的绝对路径转义处理异常 → 先 `cd` 进目标目录，再用相对文件名。
- **自算长尾比例与工具不符**：DiskSpd 百分位按文件分别输出后再聚合 → 解析时只取末尾 `Total` 段，避免被单文件表覆盖。
- **无法得到「>X ms 占比」**：DiskSpd 不提供该直方图 → 与 fio 交叉验证时只对齐吞吐与 P50/P95/P99。

### 执行环境与后台任务
- **长时压测约 2 分钟被中断**：后台任务生命周期受限 → 改用 Bash 后台运行，已验证可稳定存活 20 分钟以上。
- **从 Bash 调 PowerShell 被安全策略拦截**：执行策略限制嵌套调用 → 用 Python 子进程从 Bash 后台驱动原生 exe。
- **SSH 非交互登录失败**：缺少 SSH 依赖库 → 在隔离虚拟环境安装 `paramiko`。

### 网络、路由与诊断
- **跨网段读吞吐仅 ~113 MiB/s（约千兆线速），写却 8.4 Gbps**：NAS 默认路由指向千兆口，读响应（下行）被限 → 在 NAS 上加静态路由，使客户端网段走万兆口。
- **同一物理卷换通路性能差 4–10 倍**：两条通路走不同网络路径（跨三层 vs 同网段直连）→ 用 `ip route get` 与网口 TX 计数定位真实出口。
- **多流并发读带宽不叠加**：链路带宽硬顶 + 确定性排队 → 确认瓶颈在链路而非协议层，从路由侧解决。
- **写入生效但重启后丢失**：运行时路由未持久化 → 在 DSM 静态路由 UI 或**开机任务计划**中固化（交付前必须做）。

### 安全与权限
- **凭据管理**：账号密码只经环境变量传入，不落盘、不写入产物。
- **最小权限**：操作账号位于 administrators 组；只读查询与必要配置修改分离。
- **写操作守卫**：脚本对破坏性与配置变更命令设只读优先守卫，需显式确认才执行。
- **客户端权限**：非管理员身份无法修改 SMB 客户端注册表/配置项，需管理员执行。

## 十、可复用命令片段

```bash
# ① 静态路由修复（需在 NAS 上执行；接口未公开，走 DSM UI 或开机任务计划固化）
#   现象：默认 default via <网关> dev eth0（千兆口），跨三层下行被限
ip route add <客户端网段>/16 via <网关> dev eth2 table static-table

# ② SMB 低风险调优（仅开 2 项，其余 32 个字段零改动）
#   enable_multichannel: false → true
#   enable_aio_read:     false → true
#   注意：DSM Web API 该接口要求 form-encoded + v3 版本 + 整体覆盖（先 GET 全字段再回传）

# ③ fio 随机混合压测（VDI 验收口径）
fio --name=vdi --rw=randrw --rwmixread=22 --bs=32k --iodepth=16 \
    --numjobs=350 --size=<每任务容量> --direct=1 \
    --runtime=1800 --time_based --output-format=json+
#   取长尾：必须用 json+ 输出并校验延迟直方图 bins 存在

# ④ 诊断读瓶颈真实出口
ip route get <客户端IP>        # 看走哪个 dev
# 对比该 dev 的 TX 计数（写）与 RX 计数（读），区分上下行是否卡在不同网口
```
