# 生态项目索引与能力边界（该不该把一堆项目整合成「专家」）

> **素材**：一份 DeepSeek 社群对话（2026-11-09 抓取）+ 对其中 10 个项目的**实时核对**
> **核对方式**：`github_scout.py` 打分引擎 + GitHub 搜索接口逐个 `repo:` 精确查询（2026-11-09）
> **核对口径**：星标 / 语言 / 许可证 / 最近提交均为当天实测，**不是**对话里引用的第三方聚合站数字
>
> ⚠️ 本篇是**决策参考 + 索引**，不含可执行代码。第三方的脚本**一个都没有打包进本技能包**，
> 只做「什么问题 → 该看哪个项目 → 风险等级 → 链接」。

---

## 1. 一句话结论

**先把本技能包做深做稳，不要一开始就整合成一个「什么都会」的群晖专家。**

专家形态应该是**编排层**（识别场景 → 判断风险 → 推荐项目 → 给命令 → 要求确认 → 记录结果），
而不是把 arc/rr、NVMe 解锁脚本、Docker 模板、SPK 编译框架一股脑打进来——那样每个场景都不够可靠，
而且用户会默认你对每个第三方项目负责。

| 层 | 职责 | 现在 |
|---|---|---|

| **项目知识库** | 记录各项目的适用场景、风险、版本限制、链接 | ✅ 本篇即这一层的起点 |

| **可选执行器** | 对安全可控的项目做插件式调用，默认 `--dry-run` | ⏳ 第三阶段 |

## 3. 本技能包的能力边界

### 3.1 在包内（自己实现，可执行）

只读巡检、官方 CLI（`synouser` / `synoshare` / `synonet`）、DSM Web API、FileStation 传输、
局域网发现、NFS 导出、性能与网络诊断、DSM 与套件升级、批量文件整理、ACL/GPO/FSLogix、
硬盘兼容性（`Synology_HDD_db` 的**方法**已沉淀为 `drive-compatibility.md`，但不打包其脚本）。

### 3.2 明确划出去（只给索引，不做执行）

| 类别 | 为什么不做 |
|---|---|
| **Xpenology 引导器**（arc / rr） | 是在**非群晖硬件上装 DSM**，与本包「管理已装好的 NAS」定位正交；且涉及引导介质，错了直接开不了机 |
| **NVMe 建存储池解锁**（`Synology_M2_volume`） | 改分区层，官方不支持，失败可能丢池；必须在现场评估后手工做 |
| **套件迁移**（`Synology_app_mover`） | 依赖上一步的 NVMe 池已建好，链条长，容器/套件状态需逐个核 |
| **SPK 编译框架**（`spksrc`） | 是开发工具链，不是运维能力；体量大、依赖重 |
| **Docker 模板合集**（`gshang2017/docker`） | 内容是「别人的编排配置」，安全与版本责任无法替你承担 |
| **内网穿透 / DDNS** | 直接改变暴露面，属安全决策，不能由技能包默认开 |

### 4.1 对话里的数字有三处对不上

1. **把 arc 当成引导器的代表，漏了更大的 rr。** 实测 `RROrg/rr` **8,764** 星，
   是 `AuxXxilium/arc`（3,571）的 **2.4 倍**，且两者同为 GPL-3.0。
   对话只给了 arc 的"约 3.4k"，容易让人以为 arc 是社区主流。
2. **`synology-nas-bootstrapper` 只有 18 星，被列进「高星项目」是错的。**
   它和 3k+ 的项目并列在同一个清单里，读者会误判成熟度。实测最近提交 1.7 个月前，
   许可证 `NOASSERTION`（仓库里没有标准许可证文件）。
3. **两个项目的许可证是「不明确」而不是「有」。** `spksrc` 和 `bootstrapper` 的 GitHub
   许可证字段都是 `NOASSERTION`——这类项目**不能当依赖直接用**，要采纳必须人工读 LICENSE 文件确认。

> 结论：对话里的项目**分类框架可用，数字不可信**。它引用的是第三方聚合站（ecosyste.ms /
> git-stars / relatedrepos 等）的二手数据，星标和许可证都会滞后或标错。
> **任何要写进方案的数字，都自己抓一遍。**

## 5. 风险分级（给客户讲之前先过一遍）

| 级别 | 含义 | 典型项目 |
|---|---|---|
| 🔴 系统级 | 引导介质、分区表、存储池结构被改，失败即开不了机或丢池 | rr / arc / Synology_M2_volume |
| 🟡 配置级 | 改系统配置或数据库，可回滚但要预案 | Synology_HDD_db / Synology_app_mover / spksrc |
| 🟢 应用级 | 只影响单个服务或只读调用 | sspks / mcp-server-synology |
| ⚪ 不建议 | 维护与许可都不足，或与需求不匹配 | synology-nas-bootstrapper |

**共同前提**：所有 🔴 / 🟡 操作在客户环境都要先声明「非官方支持路径」，
并确认群晖工单不认这个前提——这和 `drive-compatibility.md` 里的口径一致。

## 6. 什么条件下才值得做成「专家」（自检 5 条）

1. 核心 skill 在 **10–20 个高频场景**下已经稳定（能复现、有回滚、有测试记录）；
2. 有**项目推荐库 + 风险分级**（本篇的第 4、5 节就是雏形）；
3. 能明确区分「只回答」和「可执行」，且可执行的默认 `--dry-run`；
4. 有**版本兼容表**（DSM 6 / 7.x / 7.4、x86 与 ARM 差异）和回归测试；
5. 第三方项目只做**索引 / 调用**，不内嵌代码（许可证与供应链都不允许）。

五条里缺任意一条，做出来的「专家」都是把风险放大的版本。

## 7. 现在该优化什么（7 条清单 · 本包已覆盖到哪）

| # | 优化项 | 本包现状 |
|---|---|---|
| 1 | 版本与机型探测（DSM 版本、架构、Container Manager 状态） | ✅ `dsm_api.py` / `nas_exec.py` 读 `/etc/VERSION` |
| 2 | 操作安全模型（只读默认、写操作二次确认、危险操作强制 dry-run） | ✅ 守卫 exit 2 + `--yes` |
| 3 | 诊断树（存储池 / NVMe / Docker 权限 / 套件源 / 网络 / 备份失败） | 🟡 分散在各 reference，缺一张总入口图 |
| 4 | 项目推荐表（问题 → 项目 → 风险 → 链接） | ✅ 本篇第 4 节 |
| 5 | 日志与审计（意图 / 命令 / 结果 / 失败原因） | ❌ 未做（脚本不落盘是刻意取舍，需另设计） |
| 6 | 测试矩阵（DSM 7.x 主流版本 × x86/ARM × 权限） | 🟡 只有零散实测记录，无矩阵 |
| 7 | 文档与免责声明（哪些操作失去官方支持） | ✅ README + 各 reference 文首均有 |

**下一步最该补的是 #3（诊断总入口）和 #6（测试矩阵）**，#5 要在「不落盘」和「可审计」之间先定原则。
