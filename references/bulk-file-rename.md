# NAS 批量文件整理：改名 / 归集 / 隔离（实战方法论）

> 实测场景：把散落在几十个目录、数万文件的媒体库按规则重命名归集
> 实测设备：DS423+（DSM 7.2 → 7.4，btrfs 存储池）
> 实测日期：2026-10-24 / 2026-10-26
>
> 本文沉淀的是**方法论与坑**，不含任何具体目录名、文件名与账号信息。
> ⚠️ 批量改名 / 移动 / 删除都是不可逆操作，动手前务必：备份 → 干跑 → 小批量 → 全量。

---

## 1. 头号原则：**WAL 先行**

破坏性批量改名，**日志必须先于文件落盘**，而且要 `fsync`。

```
❌ 错：全部改完 → 统一写 CSV  → 中途崩溃 = 明细全丢 + 原名不可恢复
✅ 对：写 WAL(append) → flush → fsync → 改一个文件 → 记录一条 → 循环
```

本次实测的教训：某次批量改名 **17124 条全部改完**，最后统一写对照表时进程崩溃
（`UnicodeEncodeError: surrogates not allowed`），**明细 17124 条全丢**。
而这台机器的 btrfs **没有开快照**（`/volume1/.snapshots` 不存在）→ 原名不可恢复。

```python
walw = csv.writer(wal)          # 注意：csv.writer，不是文件对象.writerow
walw.writerow([old, new, ts])
wal.flush()
os.fsync(wal.fileno())           # 必须 fsync，否则进程被杀也丢
os.rename(src, dst)              # 改完再写下一条
```

### 1.1 崩了怎么办：三层补救

明细丢了不等于没救，按可得性依次尝试：

1. **隔离区路径反推** —— 被移走的文件，其新路径里保留了原相对结构，可反推原名；
2. **归集清单反查** —— 之前的 move/归集 manifest 里记了 `src → dst`，精确命中；
3. **现状清单 + 规则重算** —— 兜底，但同名/冲突项无法还原，只能人工核。

本次靠 ①+② 精确回补了数百条，剩余缺口在报告里**如实标注**，不假装完整。

## 2. ⚠️ 跨 btrfs 子卷 rename 必报 EXDEV

**同一个物理卷上的不同「共享文件夹」可能是不同的 btrfs 子卷**，
`os.rename` / `mv` 跨子卷会报：

```
[Errno 18] Invalid cross-device link
```

判据（`stat` 的设备号不同就是跨子卷）：

```python
import os
os.stat('/volume1/共享A').st_dev != os.stat('/volume1/共享B').st_dev   # → True = 跨子卷
```

处理：

| **场景** | **正确做法** |
| --- | --- |
| 同子卷内改名 | `os.rename` —— 瞬时、原子 |
| 跨子卷改名 | **copy + unlink**（`shutil.move` / shell `mv` 会自动降级为复制） |
| 跨子卷移动 23725 个文件 / 23 TB | 分批 + 落盘进度日志，可断点续做 |

⚠️ `shutil.move` 虽然能跨设备，但**不报错**——它静默降级成复制，
大目录下会跑很久且看不出异常。批量场景要自己区分。

### 2.1 同理：shell glob 会漏文件

```bash
for f in "$d"/*.mp4; do ...   # ❌ 路径含 [ ] 时会被当 glob 展开 → 漏文件
```

✅ 用 `os.walk` + `os.path.splitext` 判断扩展名，别用 shell glob。

## 3. ⚠️ SMB 客户端改名会 Permission denied，但 NAS 端 root 可以

**普通用户在 SMB 上对某些目录只有读权限** → 客户端 rename 需要删除源文件的权限 →
`Permission denied`。实测 151 成功 / 198 失败。

**解法：改到 NAS 服务端用 root 执行** `mv` —— 198 个全部成功。

```
本机 SMB 客户端 rename  →  Permission denied（151/349 成功）
        ↓ 换路
NAS 端 SSH + root mv   →  全部成功，0 失败
```

传输脚本的方式（SSH exec 通道 + base64，避开引号/编码问题）：

```bash
echo <base64> | base64 -d > /tmp/x.sh && sh /tmp/x.sh
```

⚠️ DSM 上 **SFTP 写不了部分路径**（`/volume1/@appdata`、用户家目录、部分共享子目录），
必须走 exec 通道。

### 3.1 NAS 后台进程活不过 SSH 会话

实测：`setsid nohup sh x.sh &` 约 5~8 分钟后被会话清理杀掉（首版只跑到第 6 批）。

可靠做法（按优先级）：

1. **前台分批执行** —— 最简单，每批控制在超时内，逐批推进；
2. NAS 端 python3 脚本 + `setsid nohup python3 x.py`，**脚本内自己循环重扫直到无进展**；
3. 落盘日志 + 轮询日志判断进度。

## 4. 干跑（dry-run）是必须的

规则写完先干跑，把「会改成什么」打印出来逐条看。实测靠干跑抓到三个规则回退：

| **问题** | **现象** | **修法** |
| --- | --- | --- |
| 正则尾部断言误伤 | `CRC-5298` → `CRC-529` | `(?![\x20-])` → `(?![0-9])` |
| 标签表误收前缀 | `CRC` 被当画质标签剥掉 | 从标签表剔除 `CRC` 项 |
| 日期被分隔符拆开 | `1994-08-26` → `1994 08 26` | 先抽日期 token 占位保护，再还原 |

另外两个：

- **`~` 会毁掉片名** —— `ばにぃうぉ~か~` → `ばにぃうぉ か`。分集符里不要放 `~`；
- **括号内纯序号是分集号** —— `My My Mai (1).mkv` 不能把 `1` 提到最前面，要保留在尾部。

### 4.1 冲突保护

新名与同目录已有文件同名时，**不要改名**（否则会变成 `xx (1)`），记为 `RENAME_CONFLICT` 跳过。
终检要确认「同目录同名冲突 = 0」。

## 5. 隔离区：无效文件往哪放

清理出来的无效文件（0 字节、残片、遗留占位、缩略图）**不要直接删**，
先移到独立隔离区，保留原相对路径：

```
<共享>/_隔离/<日期>/<原相对路径>
```

这样随时可以整体回退。

⚠️ **统计隔离区时别跳过** `@eaDir` —— `os.walk` 里 `skip` 掉它之后
只数到 715 个，实际是 **17974 个**（其中 17259 个是缩略图）。
口径写错会让人误判清理效果。

## 6. 归集判据：宁可漏判，不可误判

涉及敏感内容分类时，**不能用题材/风格标签当判据**，必须用客观指征。

✅ 可用的客观指征：明确年龄、明确学段、明确的角色身份描述。
❌ 不能用的风格标签：特定画风词、制服类题材词、成年向的通用标签。

本次实测：某批文件命中泛化关键词 527 条 → 收紧到强指征 260 条 → 排除明确成年标注 17 条
→ 最终 243 条。复核方式：**排除隔离目录后重新扫描，剩余命中必须为 0**。

原则：**宁可漏判也不误判**。误判会把成年作品打上错误标签，代价远大于漏掉几个。

## 7. 判定「文件是否真的是有效媒体」

不要靠扩展名，要**看文件头**：

| **目标** | **魔数** |
| --- | --- |
| MP4 | 头 `ftyp` + 尾 `moov` |
| MKV | `1A 45 DF A3`（EBML） |
| AVI | `RIFF` |

某类「假视频」扩展名（如下载器的占位后缀）实测**并非都是空文件**：
容器魔数探测后发现三类 —— 完全空、**内容完整但未改名**（去后缀即可恢复为正式媒体）、
真未完成（保留并出续传清单）。

只按扩展名一刀切会误删/误判大量可恢复文件。

## 8. 收尾核对清单

```
✅ 现状清单（全量：路径 / 文件名 / 字节 / mtime）重新生成并核对数量
✅ 同目录同名冲突 = 0
✅ WAL 文件完整可读，行数与改名数一致
✅ 对照表 CSV 行数 = RENAME + QUARANTINED + KEEP 三类之和
✅ 原始相对路径可回退（隔离区保留结构 + manifest 备份）
✅ 缺口如实标注（不要用估算填空）
✅ 媒体库侧触发一次全量刷新，确认新文件名被索引
```

---

## 9. 触发媒体库重扫

改完名要让媒体库重新索引。注意区分接口：

| **接口** | **结果** | **用途** |
| --- | --- | --- |
| `POST /Library/Refresh` | 204 | 全库扫描（有效） |
| `POST /Library/Media/Updated` | 204 | 通知媒体已更新（有效） |
| `POST /Library/VirtualFolders/Refresh` | 404 | **无效**，别用 |
| `POST /Library/PhysicalPaths/Refresh` | 404 | **无效** |
| `POST /Library/Scan` | 404 | **无效** |

扫完后**再查一次条目数**确认新增路径真的被识别（扫完立即查往往还没扫完，条目会是 0）。

## 10. 排错速查

| **现象** | **根因** | **处理** |
| --- | --- | --- |
| 改完名对照表全丢 | 先改文件后写日志，进程崩溃 | WAL 先行 + fsync |
| 跨目录 rename 报 EXDEV | 两边是不同 btrfs 子卷 | copy + unlink |
| `shutil.move` 不报错但极慢 | 静默降级成复制 | 自己判 `st_dev` |
| SMB 改名 Permission denied | 用户对源文件无删除权 | NAS 端 root 执行 |
| 后台脚本中途消失 | SSH 会话结束即清理 | 前台分批 / python3 脚本自循环 |
| SFTP 写某路径 ENOENT | 该路径 SFTP 不可写 | exec 通道 + base64 |
| shell glob 漏文件 | 路径含 `[` `]` | os.walk + splitext |
| 隔离区统计偏小 | 统计时 skip 了 `@eaDir` | 口径写进脚本注释 |
| 改名后出现 `xx (1)` | 同名冲突未处理 | 冲突检测 + 跳过 + 终检 |
| 媒体库扫完条目仍为 0 | 扫描未完成就查 | 等待后再查 |
