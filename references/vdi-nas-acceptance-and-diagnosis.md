## 1. 换盘修复验收：怎么判定通过

两块阵列（SSD RAID5 / HDD RAID6）热插拔后触发重建。验收看四类证据，缺一不可：

| 类别 | 判据 | 本次实测（脱敏口径） |
| --- | --- | --- |
| 阵列状态 | 满员且 `clean` | md3 `[4/4] clean`、md2 `[8/8] clean` |
| 数据面 | 压测 0 错误 | 300/300 会话成功、160 万次操作 0 错误 |
| 分层写量 | 冷热分层生效 | SSD 97% / HDD 3% |
| 重建期业务 | 探针零失败 | 登录 p50 约 48 ms，1294 次调用 0 失败 |

**重建时长差异巨大，属正常**：SSD RAID5 约 151 分钟（408 MB/s），HDD RAID6 约 866 分钟（14.4 h，149 MB/s）。
判定重建是否被限速，看**阵列侧聚合读取是否逼近物理上限**——本次 HDD 重建期聚合读 1106 MB/s，
接近 8 盘 RAID6 读取上限，说明没被限速；同时 SSD 侧 util 1% 几乎空闲，分层把两条链路隔离开了。

**关键坑：热插拔后阵列不自动重建。** 插回盘后必须在 DSM 存储管理器确认状态变成「正在修复」，
否则会停在降级态。写入运维 SOP，别默认它自动 remap（本次 md2 是 DSM auto_remap 自动加盘，md3 不是）。

**重建对登录延迟的影响**：重建期登录 p50 与两段重建之间的空档基本持平（48.3 vs 45.8 ms），
即**重建对登录延迟没有可测量影响**——别把重建期的一切变慢都赖到重建上。

## 2. 登录风暴归因：服务端 CPU 低，但延迟随并发线性涨

这是本篇**最值钱的诊断套路**。现象：并发会话从 3 → 50，登录耗时从 54 ms 劣化到 761 ms（+1311%），
但服务端全程 CPU 只有 3–7%。两者对不上，说明**排队点不在 NAS 的 CPU 上**。

### 2.1 耗时分解先定位在哪一段

把一次「登录」拆成阶段看增量（p50）：

| 阶段 | 3 台参照 | 50 并发 | 增量占比 |
| --- | --- | --- | --- |
| 会话建连 | 31.6 ms | 449.0 ms | 大头 |
| profile 目录枚举 | 9.5 ms | 238.5 ms | 大头 |
| 目录树遍历 | 3.9 ms | 4.7 ms | 几乎无 |
| 写测试文件 | 3.1 ms | 2.9 ms | 无劣化 |

会话建连 + profile 枚举合计占增量 **91.4%**，数据面（写）完全没劣化。
结论：**慢在每个 SMB 请求的往返次数被并发放大，不是吞吐问题**，也不是 ACL/权限计算。

### 2.2 六组实验，逐层排除

| 实验 | 方法 | 结果 | 排除/确认 |
| --- | --- | --- | --- |
| 文件系统上限 | NAS 本机多进程 stat：tierfs 卷 / 同卷 btrfs / HDD 卷 btrfs | 三者均 250–300 万 ops/s，50 并发 CPU 3% | tierfs 不是瓶颈，存储侧约 200 倍余量 |
| GIL 天花板 | 1 会话1线程 / 4 进程×1线程 / 1 进程×4线程 | 2155 / 8250 / 2194 往返每秒 | **多线程零增益 → Python GIL 串行化** |
| 拓扑对照（同 50 会话） | 5×10 / 10×5 / 25×2 / 50×1 分布 | 4.09 / 1.62 / 0.81 / 0.60 ms 每往返 | 服务端负载相同却差 6.8 倍 → 客户端拓扑影响巨大 |
| 原生 SMB（同热目录） | Windows 重定向器 3→50 线程 | 12→98 ms，p95 103 ms | 单连接请求窗口排队，分布紧密 |
| 原生 SMB（不同用户目录） | 3→50 线程，各自目录 | p50 225 ms，p95 1.31 s | 唯一真实长尾疑点 |
| CPU 归属 | 压测同时 1 秒粒度采样 | smbd 合计约 1 核；客户端 68%（2.7/4 核） | 服务端远未饱和 |

### 2.3 结论与复用判据

- **约 13k 往返/秒是客户端上限**：4 核机器被 Python GIL 串行化，所谓「50 并发」在一台机器上其实是排队。
- **判据在弱客户端上不可测**：20% 劣化这类判据，在 4 核客户端上无法在不打满自身的前提下产生 50 条
  真实独立连接，测出来的是「一台弱客户端能否同时做 50 次登录」。要有效结论，需 **≥10 台物理机同时登录复测**。
- **服务端真实代价上界**：4 条独立连接 +5%（0.473 vs 0.451 ms），25 条 +45%（仍含客户端争用）。
  最有力反证是 300 会话 / 353 连接 / 8942 IOPS 时服务端 CPU 才 7.2%。
- **可复用诊断顺序**：先看服务端 CPU/IO —— 低 → 怀疑客户端；再做文件系统上限多进程 stat 排除存储；
  再做 1 线程 vs 多进程 vs 多线程对比验证 GIL；再换拓扑/换原生客户端交叉确认；最后才归因服务端。

> 唯一值得继续跟的是**跨目录长尾**（p95 1.31 s，伴随单核 90% 瞬时峰值），方向是 smbd 并发请求处理
> 与登录期 ACL / 账户查询次数——但现有证据不足以下结论，别急着改 SMB 参数。

## 3. VDI 用户盘验收矩阵（P/F/IO 各项口径）

一套可直接套用的验收项与判定口径（结果数值为脱敏实测，作参考量级）：

| 编号 | 条目 | 判定口径 | 实测量级 |
| --- | --- | --- | --- |
| P-1 | 小文件随机 IO（4K/64K） | 平均延迟 < 阈值 | 0.48 / 0.61 ms，P99 3.4 / 3.9 ms |
| P-2 | 并发会话压力（1→300） | 0 错误、CPU 远低于 70% | 300 会话 0 错误，CPU 峰值 9.6%，延迟随会话线性上升 |
| P-4 | 日常操作体感 | 打开/保存/缩略图秒级 | 0.25 / 0.26 / 0.11 s |
| P-5 | 顺序吞吐 | 区分客户端受限 vs NAS 上限 | 写 201（双流 278）/ 读 163 MB/s，客户端受限 |
| F-1 | AD 集成与权限隔离 | 本人共享可读写建删，他人共享/系统目录拒绝 | 全部符合 |
| F-3 | Office 文件锁 | 共享冲突 0xc0000043 / 锁冲突 0xc0000054 | 全部符合 |
| F-4 | 大文件完整性 | 2 GB 写入回读 SHA-256 一致 | 一致，176/147 MB/s |
| F-5 | 配额（人均 100 GB） | 超限写入被拒 | **用户级软件配额在 tierfs 上不适用，改用共享级 + 域组配额** |
| F-7 | 以前的版本 | 快照可枚举可恢复 | 52 版本 / 5 分钟粒度，ACL 在快照时冻结 |
| F-8 | 单盘热插拔 | 降级态业务不中断 | 12 万笔 6 失败（重启窗口），md3 4/4→4/3 业务不中断 |
| IO-1/2 | 整体与文件夹 IO 记录 | 24h×30s + 逐笔 + 块层 | 分层去向、写放大、元数据枚举均记录 |

**两个高频误判**：
1. **顺序 IO 区分不了介质和通路** —— HDD 顺序读也能到 1082 MiB/s；**随机 32 KiB 才是分水岭**，
   SSD 随机能力是 HDD 的 8–9 倍、随机读 P95 相差 20 倍。VDI 启动风暴与系统盘 IO 全是随机小块，
   **用户盘必须放 SSD 卷**。
2. **读瓶颈先查 NAS 路由，别先怀疑 SMB/RAID/介质** —— 默认网关指向千兆口时，跨三层下行（读响应）
   被限约 948 Mbps，上行（写数据）走万兆口不受影响，出现「写 8.4 Gbps、读约 1 Gbps」的反直觉现象。
   加一条 NAS 侧静态路由，跨网段读吞吐可从约 113 提升到约 1125 MiB/s（约 10 倍）。
   ⚠️ 运行时路由重启会丢，交付前必须**固化**。

**验收口径要写死**：块大小、随机/顺序、读写比、每 VM outstanding、预热时长 + 正式时长、
以及「抖动样本占比 > 1% 即 FAIL」这类量化判据。长时口径（30 min）往往明显差于短口径（10 min），
疑似 BTRFS(CoW) 数据集长期覆写后碎片化——**峰值 best-case 不等于验收达标**。

## 4. 轻量 SMB 并发压测：怎么安全地造 50 条真实会话

要做「N 台终端同时登录/操作」的压测，但只有少量机器时，用**多会话脚本**凑并发：
每个脚本持有 2~3 条**相互独立**的 SMB 会话（各自独立 TCP + 独立 NTLM 会话，不走 `net use`），
分散到 3 台终端，合计 50 条常驻会话。

### 4.1 关键设计

- **会话独立性**：不走 `net use`（它同一台机器只认一个会话），用 SMB 协议层直连，
  每条会话独立 TCP + 独立认证，同一台机器也能开多条。
- **epoch 对齐触发**：以整 5 分钟为基准（`offset_s = 0`），三台终端各自独立启动也会落在同一秒开跑。
  核对 `skew_ms`（实际开跑相对整点的偏差）应 < 50 ms。
- **周期之间会话不释放**：所以「50 并发」是持续存在的，不是每 5 分钟才冒一次。
- **口令不落盘**：存当前用户环境变量（如 `SMB20_PASS`），随包分发时配置里留空。

### 4.2 每周期动作与判读

```
枚举用户目录(≤200 项) → 读 4KB profile 样本 → 写 64KB → 回读校验 → 删除
```

逐会话每周期一行 JSONL，关注：`match`（回读与写入一致）、`entries`（枚举到的目录项数）、
`skew_ms`（触发偏差）、各阶段耗时。

**从 NAS 侧核对真实并发数**（看增量，先记基线再加压）：

```sh
# 445 端口连接数（注意取本端端口字段）
awk '$4=="01" && $2 ~ /:01BD$/ {c++} END{print c+0}' /proc/net/tcp
# smbd 进程数
ps -eo comm= | grep -c '^smbd$'
```

拉起脚本后应正好多出预期条数的连接与 smbd 进程。若连接数没涨，说明会话没真正独立建立，
测出来的仍是单机排队（见 §2）。

### 4.3 注意事项

- **别在阵列重建/校验期间跑**：会话虽轻，重建期会放大时延、数据不可比。
- **用户目录运行时动态枚举**，脚本里不写死人名，换共享也能用。
- **自检三档**：`--dry`（只打印解析结果）/ `--sessions 1 --once`（立刻跑一周期）/ `--cycles 2`（跑两周期退出），
  先不连网自检通了再上真并发。
- 临时文件每周期写完即删，只留一个 profile 样本常驻，清理由人工删该目录。
