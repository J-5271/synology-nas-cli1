# 性能与网络诊断（NAS 侧瓶颈定位）

> 场景：客户端抱怨「NAS 慢」，你手里只有一台 NAS、一个客户端和一条链路。
> 本文给的是**先证明瓶颈在哪一侧**的操作顺序，以及两个最容易把结论带偏的陷阱。
>
> 全部结论来自 DS918+ / DSM 7.3-81180 与 RS6426xs+ / DSM 7.4.1-90080 上的实测。
> 示例 IP 一律占位（`<NAS_IP>` `<客户端IP>` `<内网网段>`）。
> 配套脚本：`scripts/nas_nic_sample.py`、`scripts/nfs3_client.py`。

---

## 一、诊断顺序：三级对照

单看客户端报出来的数字**不足以**下结论。要按下面三层各测一遍，差的量级会对不上：

| 层 | 手段 | 回答的问题 |
|---|---|---|
| ① 客户端观测 | 基准工具自己报的吞吐（fio / diskspd / 自研客户端 / robocopy） | 「应用看到多少」 |
| ② NAS 侧链路 | **在 NAS 上采样 `/proc/net/dev`** | 「NAS 实际往网络里发了多少」 |
| ③ NAS 本机裸盘 | 在 NAS 上 `dd` 到同一个目录 | 「后端存储本身能给多少」 |

**判定规则：**

- ② ≈ ①，③ 明显更高 → 瓶颈在**协议/客户端侧**或**链路**；
- ② 明显高于 ① → **客户端消费不动**（客户端 CPU、单连接往返、GIL、小 rsize…），NAS 是无辜的；
- ③ ≈ ① ≈ ② → 瓶颈在**后端存储本身**，与网络和协议无关。

### 1.1 ② NAS 侧网卡采样（最有用的一步）

在 NAS 上给 `/proc/net/dev` 打两个时间点，做差即可。**不要用 `ifconfig` 的累计值拍脑袋，
也不要只看瞬时值**——1 秒粒度的均值就够，但要连续采几秒、并且**同步**跑负载。

```bash
# 手动版（连续 10 秒每秒一行，看 eth0 / eth2）
python3 scripts/nas_nic_sample.py --host <NAS_IP> --ifaces eth0,eth2 --seconds 10
```

> **判读要点：**
> - `TX` 大 = 在读（NAS → 客户端），`RX` 大 = 在写（客户端 → NAS）。
>   别把 RX/TX 搞反了，否则会得出完全相反的结论。
> - 必须**在负载正在跑的时候**采，且采样窗口**完整覆盖**负载段；
>   窗口没对齐时，尾部空转会拉低均值（实测均值 717 / 峰值 1202 就是这么来的）。
> - 采样要连着 NAS 的**全部网卡**。只盯一张卡会漏掉「流量其实走了另一张卡」。

### 1.2 并发梯度：区分「上限」与「单连接往返」

同一负载按 1 / 2 / 4 / 8 / 16 / 32 并发各跑一遍：

- 带宽随并发**线性上升、延迟恒定** → 单连接往返受限（客户端或被限速的单流）；
- 带宽**到某个点就不涨、延迟按并发线性放大** → 已经打到硬上限，但**这个上限是谁的要再判**；
- 带宽随并发**先升后降** → 有争抢或队列溢出。

> 实测案例：自研 Python 客户端 8 连接 855 MiB/s、16 连接 845、32 连接 839（单进程饱和），
> 换多进程后 16 连接 963、64 连接 1044 —— **同一台 NAS、同一时间**，说明前面那个平台是**客户端**的，
> 不是 NAS 的。这就是为什么必须做 ② 的采样。

## 二、陷阱一：多网卡路由（DSM 的默认路由只挂在一张卡上）

### 2.1 现象

一台 NAS 同时有千兆口（管理）和万兆口（数据）。客户端挂共享后：

- **写很快**（客户端 → NAS，走客户端选的路由，能上万兆）；
- **读被死死压在 ~110 MiB/s**（≈ 千兆线速），而且**读的延迟恒定在 ~140 ms、方差极小**。

方差极小是关键信号：**这不是资源争抢的抖动，是确定性的排队节拍**——像被一条窄管子卡住了。

### 2.2 为什么

Linux 源地址策略路由：**回程（NAS → 客户端）走哪张卡，由 NAS 的路由表决定，与入流量走哪张卡无关**。

DSM 上默认只给「管理网卡」配了默认网关，另一张卡只有直连路由。
所以跨网段访问时，NAS 把回复包从**有默认路由的那张卡**发出去 → 如果那是千兆口，读就被卡在千兆。

### 2.3 诊断（全是只读）

```bash
# ① NAS 到客户端会走哪张卡、哪个源地址 —— 一条命令定生死
ip route get <客户端IP>
#   输出里看 dev <网卡> 与 src <源地址>

# ② 看策略路由规则与各张表
ip rule list
#   DSM 典型结构：
#     0:      from all lookup local
#     2:      from all lookup static-table      <- DSM 自己维护的静态表
#     4:      from <eth0 IP> lookup eth0-table
#     5:      from <eth2 IP> lookup eth2-table
#     32766:  from all lookup main
ip route show table static-table
ip route show table main | head

# ③ 看网卡与地址
ip -brief addr show
```

### 2.4 修正（**改网络，先确认有带外管理通道**）

在 `static-table` 里给客户端网段指定走万兆口：

```bash
ip route add <客户端网段> via <万兆口网关> dev <万兆网卡> table static-table
# 例：ip route add <内网网段> via <网关> dev eth2 table static-table
ip route get <客户端IP>      # 复核：应变成 dev eth2
```

验证：重跑基准 + **重新采样 `/proc/net/dev`**，看流量是不是从目标卡出去了。

### 2.5 ⚠️ 持久化与风险（必须告诉用户）

- 实测用 `ip route add ... table static-table` 加的路由**是临时的**，
  **NAS 重启或网络服务重启就会丢**，读性能会悄悄退回千兆。
  要在 DSM 里做成持久配置（任务计划开机脚本 / 官方支持的静态路由配置入口），别只留一条内存里的路由。
- 改路由前确认**还有另一条管理通道**（KVM / IPMI / 另一网段 / 本地控制台），
  否则命令写错会直接失联。
- 这类改动属于「改设备配置」，按 `SKILL.md` 的安全红线**必须先跟用户确认**。

### 2.6 顺带排除的两个常见嫌疑

实测在同一台设备上，下面两条**都不是**读瓶颈的原因，别在它们身上浪费时间：

- **SMB Multichannel 开关**：关掉 / 打开，读带宽一模一样（112.8 MiB/s 不变）。
- **RAID 写惩罚**：写没问题（顺序写 1055 MiB/s），读才被卡住 —— 写惩罚解释不了「只读慢」。

## 三、陷阱二：口径不同（页缓存 vs 持久化）

**在 NAS 上做任何写性能对比之前，先统一口径。** 同一个卷，`dd` 的三种写法能差 3 倍以上：

| 写法 | 语义 | 实测（同一目录 / 同一卷） |
|---|---|---|
| `dd ... oflag=direct` | 绕过页缓存，不强制每次落盘 | 701 MiB/s |
| `dd ... oflag=direct,dsync` | 绕过页缓存 + **每次写都同步落盘** | **401 MiB/s** |
| `dd ... conv=fsync` | 走页缓存，末尾 fsync 一次 | **1335 MiB/s** ← 缓存吸收的假象 |

```bash
# 三种口径依次跑，先自己把量级摸清楚
dd if=/dev/zero of=<目录>/__t1 bs=1M count=16384 oflag=direct          2>&1
dd if=/dev/zero of=<目录>/__t2 bs=1M count=16384 oflag=direct,dsync    2>&1
dd if=/dev/zero of=<目录>/__t3 bs=1M count=16384 conv=fsync            2>&1
dd if=<目录>/__t1 of=/dev/null bs=1M count=16384 iflag=direct          2>&1   # 读，同样要 direct
rm -f <目录>/__t1 <目录>/__t2 <目录>/__t3
```

### 3.1 为什么这会毁掉结论

- **SMB 的 `WRITE` 是「服务端写进页缓存就回执」**，落盘是后台异步的。
  所以 SMB 报出来的写带宽是**页缓存口径**。
- **NFS 的 `WRITE` 默认 `FILE_SYNC`**，必须落盘才回执 → 是**持久化口径**。
  （实测 Synology 的 nfsd 即使收到 `UNSTABLE` 也不给写回，见 `references/nfs-service.md` 第四节。）
- 于是同一块盘上会出现「SMB 写 1100 MiB/s、NFS 写 550 MiB/s」这种数字，
  **看着像 NFS 慢一倍，其实是两个口径**。而 NAS 本机的 `oflag=direct,dsync`（401 MiB/s）
  恰好证明 550 才是这块卷**真正能持久化**的速度。

> 写结论时**必须写明口径**。对「用户点了保存不能丢」的业务（数据库、邮件 OST、文档协作），
> 只有持久化口径的数字有参考价值；页缓存口径的数字只在「吞吐型、允许掉缓存」的场景下有意义。

### 3.2 读也要注意 direct

读同理：`iflag=direct` 才是物理读。反复读同一个文件会命中 NAS 页缓存，
测出来的可能远高于介质能力（实测 O_DIRECT 读 877 MiB/s，而缓存命中时链路侧能发到 1160 MiB/s）。

## 四、实测基线（RS6426xs+ / DSM 7.4.1-90080，用于对照量级）

> 只记量级与结论，不含任何真实地址。客户端与 NAS 之间为万兆直连、
> NAS 侧路由已按第二节修正。卷为 4×SATA SSD RAID5 + Btrfs。

| 项目 | 数值 | 备注 |
|---|---|---|
| 空载 RPC 往返（NFSv3 GETATTR） | **0.106 ms**（p50 0.098 / p95 0.146） | 网络与 nfsd 都很轻 |
| 顺序读（NAS 侧 eth 实测发出） | **≈1160 MiB/s**（峰值 1202） | 这才是 NAS 能力 |
| 顺序读（自研 Python 客户端 64 连接） | 1044 MiB/s | 差值是客户端消费不动 |
| 顺序写（NFS `FILE_SYNC`） | **546–577 MiB/s** | = 持久化口径 |
| 随机读 32 KiB（16 线程） | 16 969 IOPS / 530 MiB/s，P99 < 2 ms | — |
| NAS 本机 `oflag=direct` 写 | 701 MiB/s | 物理写（异步落盘） |
| NAS 本机 `oflag=direct,dsync` 写 | 401 MiB/s | 物理写（同步落盘） |
| NAS 本机 `iflag=direct` 读 | 877 MiB/s | 物理读 |

**一句话结论**：读能跑满万兆（瓶颈在客户端）；写受后端持久化能力约束；
两者都不能用「页缓存口径」的数字去代表。

## 五、汇报模板（避免把话说满）

给结论时带上这四要素，别人才能复核：

1. **口径**：块大小 / 队列深度 / 并发数 / `direct` 与否 / 客户端工具与版本；
2. **瓶颈侧**：客户端观测 vs NAS 网卡实测 vs NAS 本机裸盘，三行数字；
3. **时间窗**：采样是不是完整覆盖了负载段；
4. **未验证项**：哪些结论是推理、哪些是实测。
